CASE 01 · 운영 이슈 판정

티켓을 만들기 전에,
문제인지 먼저 판단합니다

운영 중
80.8%정답 확보 26건의 엄격 기준 정확도

문제와 판단

협력사 제보를 프론트·서버·계산 모델부터 나누다 보니, 하위작업 23건 중 7건이 오류가 아닌 것으로 종결됐습니다. 잘못된 담당 영역으로 배정되거나 수정이 배포 직전 철회되는 일도 있었습니다.

개발 담당을 찾기 전에 제보의 사실관계를 판정하도록 순서를 바꿨습니다. 오류 아님·배포 지연·정책 미구현·개선 요청·버그·미확정으로 나누고, 필요한 경우에만 티켓을 생성합니다.

제보 접수
선례·정상 동작 확인
판정 6종
필요 시 티켓·배정

직접 수행한 일

  • 문제 분류 절차와 도메인 편람을 연결하고 AI가 따라야 할 표준 프롬프트를 구성했습니다.
  • 선행 자동화의 실패 5유형을 정리해 가드레일 7조를 설계하고 동일 조건 비교 검증을 진행했습니다.
  • 접근할 수 없는 영역은 추측하지 않고, 확인된 사실과 미확정 사항을 분리하도록 기준을 세웠습니다.

결과와 현재 상태

60건을 블라인드 분석하고 정답이 확보된 26건을 채점했습니다. 일치 21건·근접 2건·불일치 3건으로 엄격 기준 80.8%, 근접 포함 88.5%를 확인했습니다. 현재 합의된 위임 범위에서 판정·배정·협력사 회신을 담당합니다.

정확도는 사전 검증 표본의 결과입니다. 전체 운영 이슈의 지속적인 정확도나 티켓 감소율을 의미하지 않습니다.

CASE 02 · 위탁 운영 시스템

외부 위탁 업무를 위한
정보 접근 방식을 바꿉니다

구축·실사용 테스트 완료 / 운영환경 배포 대기
약 3개월문제 정의부터 설계·구축·검증까지

문제와 판단

결제 안내를 외부 업체에 위탁하면서 고객 정보를 파일로 전달하거나 원문으로 조회하는 방식에 의존했습니다. 업무는 위탁하되 정보 접근과 작업 이력을 통제할 수 있는 구조가 필요했습니다.

외부 담당자가 전용 화면에서 필요한 정보만 확인하도록 설계했습니다. 외부와 내부 화면을 분리하고 최소 노출과 행동 기록을 기본 원칙으로 삼았습니다.

사유·변경 대상 확인
승인 후 요청자 실행
실행 전 백업
결과 대조·필요 시 원복

직접 수행한 일

  • 목표 구조·업무 로직·화면 시안을 직접 작성하고 AI 코딩 도구를 활용해 구현했습니다.
  • 개인정보 기본 마스킹, 원문 확인 시 재인증, 조회·메모·발송 이력 기록을 적용했습니다.
  • 운영 원본 DB는 읽기 전용으로 연결하고, 변경 기능에는 승인·백업·검증·원복 절차를 별도로 설계했습니다.

결과와 현재 상태

본인 커밋 58건, PR 약 27건(머지 20건), 자동 테스트 180개가 구축·검증 기록으로 남아 있습니다. 로컬 서버에서 실제 업무 흐름과 예외 상황 테스트를 완료하고 배포 담당자에게 코드와 문서를 전달했습니다.

운영환경 배포는 별도 담당 작업으로 남아 있습니다. 구축·검증 완료와 실제 운영 도입을 구분하며, 시간 절감이나 정보 노출 감소를 운영 성과로 제시하지 않습니다.

CASE 03 · 고객 여정과 데이터 연결

서로 다른 시스템의 상태를
하나의 고객 여정으로 읽습니다

단계 체계 정리 / 대조 기능 구축
일 1,000건 규모자동 대조 기능이 다루는 데이터 규모

문제와 판단

CRM·DB·어드민의 단계 단위가 달라 같은 고객 건의 진행 상태를 대조하기 어려웠습니다. 단계 체류와 결제 안내 이후 활동을 확인할 기준도 필요했습니다.

단계 체계를 하나의 축으로 매핑하고 DB를 경유하는 상태 신호와 결제 신호의 분기 예외를 정리했습니다. 데이터마다 기준이 되는 시스템을 명확하게 하는 것부터 시작했습니다.

CRM·어드민 상태
공통 단계·기준 데이터
진행 중 건 재조회
불일치 확인·후속 판단

직접 수행한 일

  • CRM 단계와 DB·어드민의 하위 상태를 대응시키고 연동 방향을 정리했습니다.
  • 활동 정보와 담당자를 연결하고 금액 구간·담당자별 데이터를 분리했습니다.
  • 업무시간 매시 진행 중 건을 자동 대조하는 기능을 위탁·내부 운영 시스템에 구현했습니다.

결과와 현재 상태

담당자가 서로 다른 화면을 해석할 때 사용할 공통 기준을 마련했습니다. 자동 대조 기능은 일 1,000건 규모를 확인하도록 구축했으며, 같은 상태 모델을 유실 감시 설계의 기준으로 사용했습니다.

자동 대조 기능을 포함한 새 시스템은 로컬 검증 완료 후 운영환경 배포 대기 중입니다. 리드타임 개선 폭·전환율·위탁 배정 이후 효과는 제시하지 않습니다.

CASE 04 · 권한 체계 개선

권한을 회수하기 전에,
필요한 업무 접근을 보장합니다

적용 완료
22명 → 3명최고관리자 권한 보유 인원

문제와 판단

최고관리자 권한을 줄이면서도 실제 업무에 필요한 접근은 유지해야 했습니다. 직함만 보고 일괄 회수하면 사용자 업무가 중단될 수 있었습니다.

권한 현황과 실제 사용 기록을 함께 분석했습니다. 필요한 역할을 먼저 부여하고 기존 권한을 회수하는 순서를 정했습니다.

권한·사용 기록 분석
필요 역할 선부여
기존 권한 회수
사용자 화면 검증

직접 수행한 일

  • 활성 사용자 251명과 90일·72,414건의 활동 로그를 분석했습니다.
  • 기능 69개·역할 64개를 정리하고 변경 전 권한 스냅샷을 보관했습니다.
  • 기존 권한 배열이 교체되는 동작을 확인해 기존 권한과 필요한 권한의 합집합을 먼저 부여하도록 처리했습니다.

결과와 현재 상태

최고관리자 권한 보유자를 22명에서 3명으로 축소했습니다. 관리자 부여 기준과 직무별 권한 기준을 남기고, 자동 선택을 지원하는 도구에서도 최종 저장은 담당자가 수행하도록 했습니다.

관리자 인원은 변경 전후 수치입니다. 이 수치 자체를 보안 사고 감소율이나 전체 보안 수준으로 해석하지 않습니다.

CASE 05 · 상담 안내 도구

안내문은 자동으로 만들고,
고객 확인은 담당자에게 남깁니다

CX 파트 전원 사용
4명당시 CX 파트 전원 사용

문제와 판단

CX 지원을 위해 온보딩받으며 고객별 일자·금액·신청 정보를 여러 화면에서 찾아 정형 문구에 붙여넣는 업무를 발견했습니다. 템플릿이 있어도 고객 값을 옮기는 과정은 수작업이었습니다.

문의 인식부터 자동 답변까지 구상했지만, 고객과 문의 맥락의 확인이 필요하다고 판단했습니다. 시스템 값 조회와 문구 생성을 자동화하고 대상 지정·내용 확인·발송은 사람이 담당하도록 했습니다.

담당자가 고객 지정
시스템 값 조회
안내문 자동 생성
담당자 검증·발송

직접 수행한 일

  • 문제 발견부터 기획·설계·구현까지 직접 맡고 먼저 시범 사용했습니다.
  • 사용자 피드백을 받아 웹 계산기와 API를 통한 시스템 필드 입력 기능으로 확장했습니다.
  • 사용 방법을 공유하고 반복 개선하며 팀이 문의 대응에 사용하는 도구로 정착시켰습니다.

결과와 현재 상태

당시 CX 파트 전원 4명이 사용했습니다. 사용 경험 기준으로 메시지당 작성 시간을 1분 이상 줄였으며, 수동으로 고객 값을 옮기는 과정을 줄였습니다.

시간 단축은 사용 경험에 따른 추정치입니다. 사용자가 고객 대상을 잘못 입력하는 오류는 남아 있어 최종 확인이 필요합니다.

CASE 06 · 변경 리스크와 API 전환

변경이 고객에게 미칠 영향을
실행 전에 구분합니다

유실 감시 설계 / API 전환 완료
P0~P3비가역성과 매출 영향에 따른 설계 등급

문제와 판단

결제 신호가 CRM과 DB·알림으로 나뉘는 과정에서 일부가 유실되면 결제 완료 고객에게 독촉이 발송될 수 있었습니다. 벤더 API 종료 또한 거래 상태와 고객 안내를 함께 멈출 수 있는 변경이었습니다.

유실 감시는 개별 건을 보정하는 방식 대신 공통 대조와 등급별 정책으로 설계했습니다. API 전환에서는 공식 문서와 실제 호출을 대조해 바꿔야 할 대상과 유지 대상을 먼저 구분했습니다.

영향·복구 가능성 판단
드라이런 2주
사람 확인 후 처리
검증 후 자동화 확대

직접 수행한 일

  • 유실 이슈 4종을 P0~P3로 등급화하고 드라이런·반자동·자동의 단계 전환 기준을 설계했습니다.
  • 고객 안내 자동화 39개의 재실행 전에 실제 발송 이력을 확인하도록 운영 절차를 정리했습니다.
  • API 변경 사항을 업무 시나리오별로 검증하고 운영 반영 당일 오류 수정과 누락 구간 복구 여부까지 추적했습니다.

결과와 현재 상태

API 종료 기한 전에 운영 중단 없이 전환을 완료하고 데이터 유실 여부를 확인했습니다. 유실 감시에서는 자동 처리 권한을 넓히기 전에 확인할 기준과 안전장치를 설계했습니다.

유실 감시의 단계 전환은 설계 기준이며 전체 자동 운영이 완료됐다는 의미는 아닙니다. API 전환 완료와 별개의 상태로 구분합니다.
